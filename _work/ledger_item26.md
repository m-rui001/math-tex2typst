## 21:58 增量（台账 CRLF 事件归因更正：是行级编辑工具自己，不是别的会话）

**先记归位**：21:53 落 item 25 之后复量，台账 CR **285 → 568**（＝全文行数），纯行尾污染、内容逐字未变。用二进制整篇换行归位后 **123,731 B / 568 行 / CR 0**，两次复量同值。同一条尺现在覆盖任意路径：`_work/crlf_fix.py [--apply] [path-or-glob ...]`（无参数时仍按 `研究笔记/D*.md`），守卫是「行数不动才落盘」，孤 CR 会让行数上涨于是当场拒绝——不再另立第二把尺。全库复量：734 篇笔记＋台账 **CR 全零**；只剩 `INDEX.md`（104 枚 CRLF）与 `派单提示词.md`（90 枚 CRLF＋1 枚孤 CR，改它会涨行数，故 `lines_stable=False`）两枚非笔记文件带 CR，它们不是写手素材也不归本腿的落盘口径，只登记不动。

**归因实验（副本对照，三档）**：其一，29 B 全 LF 小文件改一行 → CR 0→0；其二，123,731 B 全 LF 副本改同一行 → CR 0→0；其三，同样长度但前 284 行写成 CRLF（实测 crlf=283）的混合副本改一行 → **CR 283 → 568（＝行数）**。结论：**行级编辑工具（Edit 一类）在「文件里已经存在 CR」时，会把整篇按 CRLF 重写；全 LF 的文件不受影响**。于是 item 16 里那条「另一会话整段重写造成的行尾污染，不回改别人的段落」**归因错了**——那 285 枚 CR 是本腿自己的编辑工具养出来的，越改越脏，而且根本没有别的会话动过这个文件。这条更正不回改 item 16 的原文（日志按落笔时的读数保留），只在此立档。

**由此定的新判据**：落盘禁 CR 的文件（笔记、台账、`next_batch.md`）动笔前先量 CR，非零就先归位再改；改写走 Python 二进制写（`_work/ledger_append.py`、`_work/crlf_fix.py`），不走行级编辑工具。写手侧不受影响：它们 Edit 追加的稿子本就全 LF，工具对全 LF 文件是良性的。

**顺带第二次证实的那条探针律**（已计入 item 25）：`python - <<'EOF'` 与 `python -c "…"` 都会吃掉一层反斜杠，源码写的 `u"\\rank"` 到 Python 手里是回车＋`ank`，于是「全库零命中」是探针碎了。判据仍是两条一起用：探针只用 Write 落文件再跑，零命中先怀疑自己的串。
